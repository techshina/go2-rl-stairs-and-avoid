## 1. 現行設計と評価結果の要約

### 構成(v2 との差分)

| 項目 | 階段特化 v2 | 階段+回避 |
|---|---|---|
| actor 観測(1フレーム) | 固有受容 45 + height_scan 187 = 232 | + 水平 2D lidar 72 = 304 |
| actor 入力(×5 履歴) | 1,160 | 1,520 |
| critic 入力(特権観測) | 247 | 319 |
| 水平 lidar | なし | 72 本・全周 5° 刻み・base+0.4m(地上約 0.7m)・5m レンジ |
| 追従報酬 | `track_lin_vel_xy_exp` | 障害物ゲート付き(コマンド方向 ±60° の最小 lidar 距離 / 1.0m でフェード) |
| 追加報酬 | − | `obstacle_proximity` −10.0(0.8m 以内、二次)、`head_contacts` −1.0 |
| ネットワーク | MLP 512→256→128, ELU, 非対称 AC | 同一 |

### 評価(2026-08-12〜24、各 200 体 × 2000 ステップ、vx=0.5 直進)

- 障害物(柱 4〜12 本 / 8m 四方): 階段+回避は**全密度で衝突 0、転倒込み失敗率 0〜3.6%**。
  v2 盲走(lidar なし・height_scan のみ)は base 衝突 0 だが**柱に足を取られた転倒が 8〜35%**。
  → lidar による早期検知(3m 以上手前で迂回)の価値が約 30 ポイントの失敗率差として定量化された。
- 階段: 11cm まで両者 0%。**13〜17cm で v2 比 数ポイント劣化**(13cm 0→3.9%、15cm 15.8→19.6%、17cm 31.3→40.8%)、
  15cm 以上で前進速度が大幅低下(15cm: 0.42 → 0.23 m/s)。19cm 以上は「登らず止まる」ため転倒率は v2 より低い。
- **長い階段(14m タイル・15 段・壁高 1.95m)では段差 13cm でも階段手前で立ち止まり登らない**。
  同じ地形を v2 は止まらず登り切る → 階段の難しさではなく lidar ゲート起因と確定。

### 根本原因

水平 lidar は高さ方向に 1 平面しか見ないため、**長い階段の壁面と柱を区別できない**。
短い階段(評価用 8m タイル・壁高 0.65m)では lidar 面が壁の上を抜けるが、長い階段では壁面を約 1.6m 先で捉え続け、
ゲートが追従報酬を削る → 前進の動機が消える。lidar 面の高さ・ゲート距離の調整は対症療法で、
「高さを区別できない」構造は残る。

## 2. 検討した改善アプローチ

### A. 水平 lidar を維持した緩和策(対症療法)

1. lidar 面を上げる(base+0.4 → +0.5〜0.6m)— 短い階段には効くが長い階段の壁(1.95m)には無力
2. gate_distance を 1.0 → 0.7m に短縮 — 反応が遅れる分、回避マージンも削られる
3. 終了ペナルティの明示化(legged-loco 方式: 接触 −5 / 終了 −200)でゲートを弱める・外す — 回避が立つかは要学習

いずれも根本(高さの区別)に触れないため、長階段スタールは形を変えて残る可能性が高い。

### B. 粗い広域 height_scan で高さごと見る(根本対応、**推奨**)

水平 lidar を外し、標高マップを広く粗く追加する。実機では現行 height_scan と同じ L1 lidar 由来の標高マップから
切り出すだけで、追加センサ・別パイプラインは不要(水平スキャンを切り出すより素直)。

#### 観測

| | 現行(細かい height_scan、維持) | 追加(粗い広域 height_scan) |
|---|---|---|
| 範囲 | 体周辺 1.6 × 1.0m | 前方バイアス x −0.5〜+4.5m、y ±1.5m |
| 格子 | 0.1m | 0.25m(柱最小幅 0.35m より細かい) |
| 点数 | 187 | 21 × 13 = 273 |
| 役割 | 足の置き場所(階段) | 障害物の早期検知(〜4.5m 先) |
| actor ノイズ | ±10cm | ±10cm + 遮蔽マスク(柱の影を未観測化) |

- actor 入力: 1 フレーム 232 + 273 = 505、×5 履歴 = 2,525 次元(現行 1,520)
- 前方バイアスは実機 L1 の後方死角に対応(2026-08-12 決定「水平 lidar は前方アークのみ」と整合)
- 遠方セルは点密度が距離の二乗で減り、柱の背後は遮蔽で未観測になる。粗い格子は計測側の都合でもあり、
  遮蔽マスクのノイズモデルが sim2real の鍵(legged-loco が先行事例)

#### 障害物セルの定義(報酬計算用、シム真値で判定)

```
obstacle[i][j] = (H[i][j] − H_foot        > h_abs )   # 足元基準で登れない高さにある
              AND (H[i][j] − nbr_min[i][j] > h_step)   # 周囲 4 近傍の最小値から 1 段で飛び出ている
h_abs = h_step = 0.35m(Go2 が登れる限界 ~30cm を根拠、カリキュラム最大段差 23cm の約 1.5 倍)
```

| 物体 | 絶対高さ | 局所段差 | 判定 |
|---|---|---|---|
| 柱 1.5m | ✓ | ✓(縁) | 障害物 |
| 箱 0.5m(将来の低障害物) | ✓ | ✓ | 障害物 |
| 階段 4 段先(+0.92m) | ✓ | ✗(23cm) | 地形 |
| 階段 1 段先(+0.23m) | ✗ | ✗ | 地形 |

- 絶対高さ 1 本(例 0.8m)は階段を確実に外せるが 0.4〜0.8m の低障害物を全て見逃すため不採用
- 局所段差 1 本は格子幅と段幅の関係に敏感(1 セルに 2 段入ると 46cm で誤判定)で不採用
- 2 条件の AND で「遠くの高い段」は第 2 条件で、「近くの低い段」は第 1 条件で除外される
- 柱の中央セル(周囲もすべて柱)は第 2 条件で抜けるが、距離計算は最も近いセル(=柱の縁)なので影響なし
- 格子 0.25m ≤ 段幅 0.3m を守る(安全側なら 0.2m 格子 / h_step 0.4m)。判定はノイズなしの真値で行う

#### 報酬(現行の 2 関数の中身のみ差し替え、weight・パラメータは維持)

- ゲート付き追従: `d_min` = コマンド方向 ±60° 内の**障害物セル**までの最短距離(なければ max_range)、
  `gate = clamp(d_min / 1.0m, 0, 1)`。階段セルは障害物に入らないので、登坂中もゲート = 1
- 近接ペナルティ(−10.0): **最も近い**障害物セルの距離 d で `((0.8 − d).clamp(0) / 0.8)²`。
  現行のレイ平均から min ベースへ(セル数が状況で変わるため)
- `head_contacts`(−1.0): 接触力センサ判定で外界知覚センサに依存しないため変更なし
- 終了条件・地形・カリキュラム・ネットワーク: 変更なし(v2 / 現行との比較可能性を維持)

#### 強化学習への組み込み方

判定ロジックは**報酬関数の中にだけ**入れ、ポリシーには入れない。

| 層 | 渡す/計算するもの | 判定ロジック | 実機で動く |
|---|---|---|---|
| 観測(actor) | 粗い height_scan の生の高さ値(ノイズ付き) | 入れない | 動く |
| 報酬 | ゲート付き追従・近接ペナルティ | **ここで使う**(真値) | 動かない(学習時のみ) |
| critic | 生の高さ値(ノイズなし)+ 特権観測 | 入れない | 動かない |

理由: 観測に bool フラグを入れると実機でも同じ判定モジュールが必要になり、しきい値ずれやマップノイズが直接行動に響く。
生の高さを見せれば「0.35m の箱は避ける、0.2m の段は登る」という連続的な判断をネットワークが自分で獲得できる。
現行設計も同じ思想(lidar 生距離を観測に、「1m 以内=危険」は報酬にのみ)で、3m 以上手前から回避する挙動を獲得している。

## 2.5 実装と検証結果(2026-08-28)

タスク `Unitree-Go2-Velocity-ObstacleHM` として実装(`go2_obstacle/heightmap_mdp.py`、`velocity_heightmap_env_cfg.py`)。

**スモークテスト**(`smoke_heightmap.py`、当時のフォークで実施・現リポジトリからは削除済み。地形 5 種・難易度 1.0):

| 地形 | 障害物セル | ゲート |
|---|---|---|
| 柱 12 本(cfg height 1.5) | 9〜10 | 1.0(1m 以内になし) |
| 柱 60 本 | 29 | 1.0 |
| 低い箱(cfg height 1.0 → 実効 0.5m) | 14 | 1.0 |
| 階段 23cm(逆ピラミッド、ピット底から) | **0** | 1.0 |
| 階段 13cm(下り) | **0** | 1.0 |

観測次元は設計どおり actor 2,525 / critic 520。格子の reshape 向き(x=列)も ASCII マップで確認。

**発見: 柱の実効高さは cfg の半分。** Isaac Lab の `repeated_objects_terrain` は箱を z=0 中心に置くため、
`height=1.5` の柱は地上 **0.75m** しか出ていない(スモークテストの高さ読みで判明)。既存の lidar 版の学習・評価も
すべてこの条件で行われており、「高さ 1.5m の柱」という記述は不正確。lidar 面(地上約 0.72m)と柱天面(0.75m)の
余裕は数 cm しかなかったことになる。新タスクでは比較可能性のため地形は据え置き(0.75m > h_abs 0.35m で余裕あり)。

**サニティ学習**(30 iter): 31,300 steps/s(lidar 版の 88%)、10,000 iter ≈ 8.7h。本学習を 2026-08-28 に開始
(`logs/obstacle_hm_train.log`、`logs/rsl_rl/unitree_go2_velocity_obstaclehm/`)。

## 4. その他の課題(記録)

- 回避動作の滑らかさ: ゲートは「塞がれたら追従報酬を消す」だけで回避中の動作の質に報酬を与えていない。
  密度が高いと「歩く→ためらう→曲がる」のカクつきが目立つ。回避中も「空いている方向への前進」に報酬を出す設計を検討
- 評価タイル外周が空き地のため「場外へ逃げて達成」が混在し得る(フェンス付き / ゴール到達型で排除)
- 「衝突率」は base 接触判定限定の値。実際の失敗は脚が柱に触れて転倒(bad_orientation)に計上されるため、
  失敗率は必ず「衝突+転倒」で報告する
- v2 は「no lidar」ではない: height_scan 自体が実機では L1 lidar 由来。正確には「水平 lidar なし」


## 4.5 第3案: 拡張細格子(単一グリッド、2026-09-01 設計検討のみ・未実装)

粗格子を足す代わりに、既存の細かい height_scan を前方 +1.2m・左右 ±0.5m 拡張する案
(x −0.8〜+2.0m × y ±1.0m、0.1m 密度のまま 29×21 = 609 点)。

- **本命構成は「スキャン履歴 1 フレーム化」とセット**: actor = 固有受容 45×5 + スキャン 609×1 = **834 次元**
  (階段特化 1,160 より小さい)。知覚 0.8→2.0m 拡張と次元削減が同時に成立する
- Isaac Lab は履歴を項ごとに設定可能(observation_manager.py:551 — group の history_length が None のときのみ
  term 個別値が生きる)。v2 系は group=5 を設定しているので、この案では group を None に戻し
  固有受容 6 項に term 個別で 5 を設定する
- 利点: 解像度境界なし・実機は標高マップ 1 切り出し・0.1m 密度で細ポール(r<0.18)も検知可・判定式は細格子で検証済み
- 弱点: 検知 2.0m がマージン上限(HM v2 実測 1.6〜3.4m の上側は出ない)。全項 ×5 のままだと 3,270 次元で逆効果
- ウォームスタート互換: 拡張格子は元の 17×11 領域を部分格子として含むので、特化の scan 重み(最新フレーム分)を
  対応列へ移植可能(履歴 1 化により旧フレーム分の重みは捨てる=bit 一致は失われる)
